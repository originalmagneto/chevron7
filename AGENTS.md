# AGENTS.md - Chevron7 macOS UI

## Project Overview
Chevron7 is a 100% native macOS SwiftUI application for Qualified Electronic Signatures (KEP / eIDAS) and Guaranteed Conversion of legal documents (Zarucena konverzia according to Slovak Law No. 305/2013 Z. z. and Decree No. 70/2021 Z. z.). Its signing engine is a fork of slovensko-digital/autogram (see NOTICE).

## Architecture & Tech Stack
- Swift 6.0+ / Xcode 27.0 toolchain (`/Applications/Xcode.app`)
- Native macOS SwiftUI (`NavigationSplitView`, `.regularMaterial`, `.ultraThinMaterial`, Liquid Glass design)
- Evidence register of conversions as JSON in `Evidence/register.json` (`LocalEvidenceStore`, CEZZK integration); no Core Data or SQLite
- PKCS#11 bridge for Slovak eID cards, SAK advocate cards, and Disig smartcards
- Signing with mobile (`Signing/AVM/`): `AVMClient` talks to the Autogram v mobile relay (`https://autogram.slovensko.digital/api/v1`, 32-byte key in `X-Encryption-Key`, `POST /documents`, QR link `/qr-code?guid&key`, polling `GET /documents/{guid}` with `If-Modified-Since`); `AVMSigningSession` drives upload, polling, timeout and cancel; `MobileSigningCoordinator` and `MobileSigningSheet` present the QR code; `SigningSessionStore.sign(viaMobile:)` and `ZakoSessionStore.authorizeAndSign(viaMobile:)` swap only the final signing step; ZaKo refuses a non-mandate signature (`AVMResultMapper.isMandate`). Mobile signing has a second method, eIdentita (`Signing/AGP/`): `AGPClient` creates a `qes` bundle on the Autogram Portal (`POST api/v1/bundles`, self-signed ES256 JWT per request from the Keychain key plus the portal organization (tenant) id kept in `AppSettings.agpUserID` (since the portal's tenants of 2026-09-30 the key lives in the organization settings, `sub` = tenant id, and the organization needs the admin-enabled "API prístup" feature; Settings default to the staging portal `https://agp.dev.slovensko.digital` (`AGPClient.defaultBaseURL`, the owner's decision of 2026-10-06, because Slovensko.Digital grants API access there today; production is `agp.slovensko.digital`, `productionBaseURL`) and list the portal-side steps (`EidentitaSetupSheet.steps`)), no `container`, `;base64` content), reads the contract id from bundle show, parses the `sk.minv.sca://` QR out of the unauthenticated eIdentita session page (HTML-unescaped), and polls `signed_document` until a version newer than the pre-session baseline appears; `EidentitaSigningSession` mirrors the AVM state shape, `sign(mobileMethod:)` picks the backend, no mandate check outside ZaKo, and ZaKo stays card/AVM-only. The AVM app only opens links for the public host, so `AppSettings.avmBaseURL` is test-only. Design and plan: `Chevron7/docs/superpowers/specs/2026-09-11-avm-mobile-signing-design.md`

The password lives only in the Keychain (`app.slovensko.chevron7.ezzk.soap`), the token only in memory. The engine signs a record XDC alone and locally, with no network call (`SigningParameters.isPlainRecordXdc()`, bare MIME `application/vnd.gov.sk.xmldatacontainer+xml`, `SigningRequest.signsAsRecordContainer`). ZaKo signs the record with the same PIN right after the client document, outside Demo passing only the built-in qualified TSA endpoints to the engine (`TimestampAuthority.qualifiedURLs`) so both signatures get a qualified timestamp by construction; the QTS toggle is shown only in Demo. The signed record is stored only in `Evidence/records/<id>.asice` (the copy `ReceiveConversionRecord` sends), and the Register saves it as `<number>.record.asice` ("Uložiť záznam…", `EvidenceRegisterDetail.storedRecordContainer`); a lookup result 106 is asked again once with the record's conversion time, and a 105 on that retry still means EZZK holds records under the number (ruling R-B3-1), so the row keeps code 106 and EZZK's text; a late row is still sent with a warning, and only a record EZZK refused at submission can be resent, by hand in the Register after a confirmation that carries the same lateness warning when the record is now late; the outcome-unknown message names a server fault too, not only a lost connection); `EvidenceNumberPool` remembers evidence numbers this app allocated and not yet used, per mode and Bratislava day, and reuses one instead of asking EZZK again (code 113 is the account's limit of unconsumed numbers); a number leaves the pool once the signed client container carries it or its register row is deleted, and ZaKo registers the `.signed` row before signing the record, held from the status checker until that signature ends (`EZZKStatusChecker.hold`); deleting a row (`EZZKStatusChecker.delete(id:)`) refuses while it is held or in flight, so an in-progress signature or send cannot be resurrected by a delayed write (`EZZKStatusChecker.busyDeleteMessage`); `EZZKStatusChecker` sends and checks register rows every five minutes (regular app launch only, `EZZKStatusChecker.shouldRun`, never in `--web-signing` accessory mode), one row at a time, always against the EZZK mode that allocated its number (a row is sent only while that mode is current, but an accepted or unknown row is looked up in its own mode from any mode, also by "Overiť v EZZK", since a lookup only reads), and never touches a row written before part B2 (no stored `ezzkMode`) or a production row the policy refuses (`EZZKError.submissionUnavailable`). Tests never touch the real Keychain (`makeSettingsStore(ezzkAccountController:)` with `MemoryCredentialStore`).

## Design System & UI/UX Structure

Paid authorities with credentials have no Settings UI yet. Trusted lists (`MachineTrustService`, `TrustedListCacheLoader`, `TrustedListAvailability`): a visible stamp and a trusted validation load the EU lists of the `DEFAULT_TRUSTED_LIST` countries (`UserSettings.defaultTrustedList()`: SK, CZ, AT, PL, HU, BE, NL, ES; `MachineSettings` never reads the Java preferences it shares with the upstream Autogram app, whose stored `TRUSTED_LIST` of `...,NL,LT` silently dropped Spain) in parallel (one thread per country plus two, because DSS runs every list on the pool the loading task waits in), each download capped at 30 s from connect to last byte (10 s connect, 30 s read) and all of them at 45 s inside the 60 s load, so one dead server (tsl.belgium.be gave no answer on 2026-10-02) or a trickling one (tsl.digital.gob.es, 3 MB at about 26 KB/s, about 2 minutes) no longer keeps the others out; a download still running when the load ends is never cancelled, so it finishes in the background and stores its copy for the next signature. Each list keeps its last good copy in `AUTOGRAM_TRUSTED_LIST_CACHE` (the app sets `~/Library/Caches/Chevron7/Trusted Lists` through `ProcessConfiguration.signingHelperEnvironment(cacheRoot:)`; the temporary directory otherwise), fresh for 6 h, used for up to 7 days while its server fails, and replaced only by XML; a list whose download just failed (timeout, connection error, not XML) is not asked again for 5 minutes while a last good copy exists (`TrustedListCooldown`, shared by every load in one engine process), so a long-lived session goes straight to that copy; without one the server is always asked. The downloads trust the JDK roots plus the macOS system roots (`KeychainStore-ROOT`, `TrustedListCacheLoader.tlsTrustStore`), because www.nccert.pl (PL) and nmhh.hu (HU) chain to Certum Trusted Root CA and Microsec e-Szigno Root CA 2009, which the JDK's cacerts lacks, so those two lists never downloaded before (PKIX path building failed). The load fails (`TRUSTED_LIST_UNAVAILABLE` without a country) only when no configured list came in; a timestamp's qualification never refuses a signature (upstream Autogram never checked it): after a visible Baseline T signature `file.completed` carries `timestampQualification` (`qualified`, `notQualified`, or `unverified` with the `country` whose list did not load, from the timestamp certificate, `TimestampTrustAnchors`), parsed into `TimestampQualification` on `SignedConversionResult`, shown on the done screen and, per authority for the app run, under the picker (`SigningSessionStore.selectedAuthorityQualificationNote`); a list load that fails entirely leaves it unverified instead of stopping the signature, and Baseline B loads no lists at all. A validation then shows a signature anchored in a missing list as undetermined instead of failing the whole tree. Before a PAdES signature of an unsigned PDF whose AcroForm says `/NeedAppearances true` (web form exports such as JSF pages), `SigningJob.build` passes it through `PdfFormAppearances`: PDFBox's stock AcroForm fixup adds a default `/DA` and `/DR` (Helv, ZaDb) when missing, builds every field's appearance stream and clears the flag, appended as an incremental update after the untouched source, because Acrobat shows no signature at all for a signed revision that still asks it to redraw the fields (verified 2026-10-02). This covers the machine path and the Quick Action; an ASiC-E keeps the source as its data object, and an already signed, encrypted or unbuildable PDF is signed unchanged, so Acrobat may still hide a signature added to one. Findings: `Chevron7/docs/PADES-NEED-APPEARANCES-FINDINGS-2026-10-02.md`.

## Build & Test Instructions
- Build the signing engine first (once, or after changes in `engine/`): `scripts/build-engine.sh` (needs an arm64 JDK 25 with JavaFX jmods, Azul Zulu FX 25, under `~/Library/Java` or `AUTOGRAM_JAVA_HOME`; output `.build/engine/Contents`)
- Run build script: `DEVELOPER_DIR="/Applications/Xcode.app/Contents/Developer" ./build_app.sh [--release] [install]` (bundles `.build/engine/Contents` into `Contents/{Helpers,app,runtime}`; without it signing falls back to Keychain/DEMO and the Quick Action cannot sign)
- Run test suite: `DEVELOPER_DIR="/Applications/Xcode.app/Contents/Developer" swift test`
- Tests never touch the real `~/Library/Application Support/Chevron7` (the evidence register is a legal record) or `~/Library/Caches/Chevron7`: App tests build settings with `makeSettingsStore()` (a temporary `AppSettingsStore.storageRoot`, from which evidence, vision bank, output, templates and signature images derive), Kit tests pass `directory:` / `cacheRoot:` / `applicationSupportRoot:`. `RealStorageGuard` (`Tests/Chevron7TestSupport`, installed when the test bundle loads) fails any test that changes either folder, and `RealStorageGuardTests` rejects test sources that build a store on the default root. Tests never write a named `UserDefaults` suite either (it stays in `~/Library/Preferences` for good): pass `MemoryUserDefaults()` (`Tests/Chevron7TestSupport`) to any `defaults:` parameter; the guard also fails a test that creates or changes a `~/Library/Preferences` plist named after a test class (such as `SigningBatchTests.<UUID>.plist`), and the source scan rejects `UserDefaults(suiteName:` in tests. Nor do tests use `UserDefaults.standard`, which under XCTest is the runner's own domain (`~/Library/Preferences/com.apple.dt.xctest.tool.plist`, shared by every run): `AppSettingsStore` and `AppSettings.load(defaults:)` / `save(to:)` take the defaults, `makeSettingsStore()` passes a `MemoryUserDefaults()`, and the guard fails a test that changes a key of that domain
- Probe the AVM server end to end: `swift run avm-probe <file.pdf|file.asice> [--level PAdES_BASELINE_T] [--container ASiC-E] [--out <dir>] [--timeout <s>]` (prints the QR link, opens the QR PNG, waits for the phone, prints signers)
