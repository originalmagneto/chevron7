# AGENTS.md - Chevron7 macOS UI

## Project Overview
Chevron7 is a 100% native macOS SwiftUI application for Qualified Electronic Signatures (KEP / eIDAS) and Guaranteed Conversion of legal documents (Zarucena konverzia according to Slovak Law No. 305/2013 Z. z. and Decree No. 70/2021 Z. z.). Its signing engine is a fork of slovensko-digital/autogram (see NOTICE).

## Architecture & Tech Stack
- Swift 6.0+ / Xcode 27.0 toolchain (`/Applications/Xcode.app`)
- Native macOS SwiftUI (`NavigationSplitView`, `.regularMaterial`, `.ultraThinMaterial`, Liquid Glass design)
- Core Data / SQLite for Evidence and Conversion registers (CEZZK integration)
- PKCS#11 bridge for Slovak eID cards, SAK advocate cards, and Disig smartcards
- Signing with mobile (`Signing/AVM/`): `AVMClient` talks to the Autogram v mobile relay (`https://autogram.slovensko.digital/api/v1`, 32-byte key in `X-Encryption-Key`, `POST /documents`, QR link `/qr-code?guid&key`, polling `GET /documents/{guid}` with `If-Modified-Since`); `AVMSigningSession` drives upload, polling, timeout and cancel; `MobileSigningCoordinator` and `MobileSigningSheet` present the QR code; `SigningSessionStore.sign(viaMobile:)` and `ZakoSessionStore.authorizeAndSign(viaMobile:)` swap only the final signing step; ZaKo refuses a non-mandate signature (`AVMResultMapper.isMandate`). Mobile signing has a second method, eIdentita (`Signing/AGP/`): `AGPClient` creates a `qes` bundle on the Autogram Portal (`POST api/v1/bundles`, self-signed ES256 JWT per request from the Keychain key plus settings user id, no `container`, `;base64` content), reads the contract id from bundle show, parses the `sk.minv.sca://` QR out of the unauthenticated eIdentita session page (HTML-unescaped), and polls `signed_document` until a version newer than the pre-session baseline appears; `EidentitaSigningSession` mirrors the AVM state shape, `sign(mobileMethod:)` picks the backend, no mandate check outside ZaKo, and ZaKo stays card/AVM-only. The AVM app only opens links for the public host, so `AppSettings.avmBaseURL` is test-only. Design and plan: `docs/superpowers/specs/2026-09-11-avm-mobile-signing-design.md`
- EZZK (`Chevron7Kit/EZZK/SOAP/`, `Chevron7App/EZZK/EZZKAccountController.swift`): the Ditec WCF SOAP service with the advocate's own EZZK name and password (`LogInService.svc`, token as cookie `IamTokenDescriptor`, SOAP 1.2 with mandatory WS-Addressing headers). The password lives only in the Keychain (`app.slovensko.chevron7.ezzk.soap`), the token only in memory. Settings offer Demo / Test / Produkcia (`AppSettings.ezzkMode`); test trusts only the pinned self-signed certificate (`EZZKEnvironment.pinnedCertificateSHA256`, expires 2026-10-20). `EZZKProductionPolicy` decides every consequential production call (allocating or consuming an evidence number, sending a record): open for everyone since v0.12.0 (`EZZKProductionPolicy.enabledForEveryone`, true, the owner's decision on 2026-09-24; the owner switch `EZZKProductionOwnerSwitch` is still read but changes nothing), read at the SOAP client and adapter, the status checker, the Register's and ZaKo's Done screens, and Settings, with every test and `ezzk-probe` defaulting to refused; "Vyžiadať čísla" stays test only regardless. Outside Demo mode ZaKo refuses to allocate a number or authorize with the Demo signing provider (`EZZKError.demoSignatureOutsideDemo`), so a build without the bundled engine or a card identity never costs a real number or reaches EZZK. ZaKo refuses a number allocated on another Bratislava day or fetched in another EZZK mode (`EZZKEvidenceNumberPolicy`, `AttestationData.evidenceNumberMode`). Request bodies are validated against `docs/reference/ezzk-soap/2026-09-17/`. The Keycloak OAuth/REST client (`EZZKSessionController`, `EZZKClient`) stays unwired for a future slovensko.sk login. Integration guide (setup, verified contract, error mapping, probe, maintenance): `Chevron7/docs/EZZK-INTEGRATION.md`; design: `Chevron7/docs/superpowers/specs/2026-09-17-ezzk-soap-design.md` (part A), `Chevron7/docs/superpowers/specs/2026-09-23-ezzk-part-b-design.md` (part B); findings and open gaps: `Chevron7/docs/P2E-EZZK-FINDINGS.md`
  - Record submission (EZZK part B2): `ConversionRecordRenderer` renders the record 1.0 (`50349287.ConversionRecordOfPaperToElectronicDocument.sk`) from `ConversionFormModel`, validated by `FormSchemaValidator` against the libxml2-compatible `docs/reference/forms/record-1.0/schema.validation.xsd` (the XDC itself still references and digests the official `schema.xsd`), and packaged by `ZakoRecordDeliveryBuilder` as `<number>.record.xml.xdcf`. The engine signs a record XDC alone and locally, with no network call (`SigningParameters.isPlainRecordXdc()`, bare MIME `application/vnd.gov.sk.xmldatacontainer+xml`, `SigningRequest.signsAsRecordContainer`). ZaKo signs the record with the same PIN right after the client document, outside Demo passing only the built-in qualified TSA endpoints to the engine (`TimestampAuthority.qualifiedURLs`) so both signatures get a qualified timestamp by construction; the QTS toggle is shown only in Demo. The signed record is stored only in `Evidence/records/<id>.asice` (the copy `ReceiveConversionRecord` sends), and the Register saves it as `<number>.record.asice` ("Uložiť záznam…", `EvidenceRegisterDetail.storedRecordContainer`); after a card signature the folder next to the source holds only the client ASiC-E (PDF/A and clause XDCF signed together), whose name the row keeps in `EvidenceRecord.deliveredFileName`, while the phone route (Demo only) also writes the PDF/A and the clause next to its PDF-only container; a signing failure leaves the client outputs delivered but the row `.recordUnsigned`. `EZZKSOAPClient.receive` sends it and returns the WS-Addressing `MessageID` as `EZZKSOAPSubmissionReceipt`; `ReceiveConversionRecord` consumes the evidence number on acceptance. `EZZKSubmissionCoordinator` owns every state transition (nothing-was-sent errors requeue, an unresolved outcome is looked up before any resend, a lookup code other than 0, 1, 105 and 106 means EZZK processed and rejected the record; a lookup result 106 is asked again once with the record's conversion time, and a 105 on that retry still means EZZK holds records under the number (ruling R-B3-1), so the row keeps code 106 and EZZK's text; a late row is still sent with a warning, and only a record EZZK refused at submission can be resent, by hand in the Register after a confirmation that carries the same lateness warning when the record is now late; the outcome-unknown message names a server fault too, not only a lost connection); `EvidenceNumberPool` remembers evidence numbers this app allocated and not yet used, per mode and Bratislava day, and reuses one instead of asking EZZK again (code 113 is the account's limit of unconsumed numbers); a number leaves the pool once the signed client container carries it or its register row is deleted, and ZaKo registers the `.signed` row before signing the record, held from the status checker until that signature ends (`EZZKStatusChecker.hold`); deleting a row (`EZZKStatusChecker.delete(id:)`) refuses while it is held or in flight, so an in-progress signature or send cannot be resurrected by a delayed write (`EZZKStatusChecker.busyDeleteMessage`); `EZZKStatusChecker` sends and checks register rows every five minutes (regular app launch only, `EZZKStatusChecker.shouldRun`, never in `--web-signing` accessory mode), one row at a time, always against the EZZK mode that allocated its number (a row is sent only while that mode is current, but an accepted or unknown row is looked up in its own mode from any mode, also by "Overiť v EZZK", since a lookup only reads), and never touches a row written before part B2 (no stored `ezzkMode`) or a production row the policy refuses (`EZZKError.submissionUnavailable`). Tests never touch the real Keychain (`makeSettingsStore(ezzkAccountController:)` with `MemoryCredentialStore`).
- Browser signing (`Sources/Chevron7WebBridge/`, `Sources/chevron7-webbridge-agent/`, `Sources/Chevron7WebExtensionHandler/`, `WebExtension/`): a Safari web extension owns `window.ditec` on state portals and signs through this app. Transport is native messaging only, with no HTTP port: launchd owns Mach service names, so `chevron7-webbridge-agent` (a LaunchAgent installed by `scripts/install-webbridge-agent.sh`) holds the name as a rendezvous, the app registers an anonymous `NSXPCListener` endpoint with it, and the sandboxed appex asks for that endpoint and then talks to the app directly. The agent forgets the app's endpoint when the app's connection to it ends (`WebBridgeEndpointRegistry`) and starts the app on demand with `--web-signing` (only when it is not already starting; launching it re-registers the bundle and the extension manager ends the appex mid-request, so `background.js` repeats the harmless status request, never a signing request) (`AppLaunchMode`): an accessory app with the main window suppressed (launch behavior, restoration and the untitled window all refused), which turns regular and opens its main window on reopen or Settings. Safari ends the extension's background worker after about 30 seconds and then answers `runtime.sendMessage` with `undefined`, so `ditec.js` never waits on one native message: `sign-begin` returns a job ID (`WebSignJobStore`) and `sign-result` is polled every 1.5 s until done. Every request raises a floating panel (`WebSigningPrompt`) centered over Safari's front window (`WebSigningPanelPlacement`), without a Dock bounce, because a background app cannot take focus since macOS Sonoma; nothing signs without confirmation there, with a card or with a phone over NFC. The panel shows every PDF page with Quick Look (`WebSigningDocumentPreview`). While it is open it watches for a card: an eID reads no certificates first (the engine picks the token's only signing key, serial `MachineSigningService.SIGNING_KEY_ON_TOKEN`), and during signing the eID client's `VirtualKeyboard` takes the BOK (the panel drops to normal level, activates that process and orders itself just beneath its window); any other card focuses the PIN field and Return reads the certificates first. `SigningIdentityInfo.usesProtectedAuthenticationPath` holds that split for the panel only; the main window keeps its PIN field. The portal decides the format and asks for Baseline B; the qualified timestamp switch is off for every request and never remembered, warns when it adds a timestamp the page did not ask for, and is not offered at all on slovensko.sk (`WebSignRequest.allowsAddedTimestamp`, from the `pageHost` the content script sets), which rejects such a signature. `WebSignRequest.wantsASiCContainer` turns a PDF for `getSignatureWithASiCEnvelopeBase64` (nove.slovensko.sk) into a XAdES ASiC-E container on the card and the phone path. Machine protocol sign requests carry optional eForm and XDC attributes so `XDCBuilder` and the UPVS, ORSR and FS resolvers in the bundled engine are reachable from Swift, and `SigningParameters.buildParameters` is shared with the engine's own HTTP entry point so the two cannot drift. Wire format between extension and app is covered by `WebSignRequestWireFormatTests`: both sides encoding with Swift hides real mismatches. `scripts/safari-spike.sh` checks everything that does not need Safari; `swift run webbridge-probe --sign <file>` exercises the whole app-side path. Design: `Chevron7/docs/superpowers/specs/2026-09-11-safari-extension-design.md`; background launch: `Chevron7/docs/superpowers/specs/2026-09-16-web-signing-background-design.md`; what broke on nove.slovensko.sk with I.CA, eID and the phone, and why (Baseline B, nested ASiC-E, forced eID login, Safari worker lifetime, appex restarts): `Chevron7/docs/WEB-SIGNING-FINDINGS-2026-09-16.md`
- PDFKit, CoreGraphics, Apple Vision and FoundationModels for document analysis and security element detection
  - `LayeredDetectionProvider` (VisionAI/): one render plus fast and accurate OCR per page (`AccurateTextExclusions`); candidates from `BuiltInVisionProvider` (frozen, fed the shared exclusions), `DetectContoursRequest`, objectness saliency; merged by `CandidateMerger`, pruned by `CandidateQualityFilter` (text coverage, ruled boxes, ink inside OCR); classified by `TwoStageClassifier` (`FeaturePrintClassifier` kNN over `ExampleBank`, then on-device `FoundationModelClassifier` with a fresh session per crop, no heuristic hint, decisive negatives, 12 crops per page); `DetectionRunStats` carries model calls, unsure calls, filtered candidates and model seconds; `LearnedCandidateSource` proposes hinted boxes from the reviewer's own trained model when one is active (audit id `learned(<sha>)` in the identifier)
  - `RealScanSmokeTests` runs the whole pipeline on a local scan named by `CHEVRON7_DIAG_PDF` (skips without it); time it in release with `caffeinate -dimsu swift test -c release -Xswiftc -enable-testing`
  - `ExampleBank` at `~/Library/Application Support/Chevron7/VisionBank` records confirm/reject decisions; `CreateMLExporter` writes Create ML object-detector datasets; `vision-eval` target scores precision/recall; `vision-train` spike trains on an exported dataset and prints time, memory and per-label metrics; in-app training (`DetectorTrainer`, `DetectorPromotion`, `ModelRegistry`, readiness report and estimate) runs once at a time from the reviewer's own workflow window and only proposes; model transfer (`ModelTransfer` zip of `Detector.mlmodel` plus `metadata.json` via `/usr/bin/ditto`, SHA check, import staged as a candidate through the same promotion gate, cancellable staging and scoring)
  - Security elements: `SecurityElementCatalogue` retains legacy persisted kinds and adds binding cord, sealing tape, wax seal and material protections. `observation` separates scan regions from physical-original review; physical entries require textual location and an explicit output page, never train crops. Human certification maps to generic visual labels. Originals without security elements require `noSecurityElementsConfirmed` plus page review. Confirmed findings reversibly override blank-page detection; free-form kinds retain required human descriptions.
  - Learning: `reviewed-pages.json` stores complete page annotations separately from crop decisions; serial `ZakoSessionStore` bank work invalidates page reviews on edits. Create ML exports only complete pages into a fresh folder, with document-level `splits.json`. Settings waits for pending learning writes before export/deletion. Physical observations exclude both their original and referenced output pages from training. Opening a document recalls its complete page reviews from `reviewed-pages.json` in place of detection on those pages (`ReviewedPageRecall`, pending suggestions, only with learning on; "Znova analyzovať AI" detects afresh), and an analysis replacing the suggestions never removes bank entries or invalidates page reviews. `ExampleBankRecorder` embeds crops at the detector's render width (`LayeredDetectionProvider.defaultRenderTargetWidth`, 760 px; PNGs stay 1200 px), and a bank example within `FeaturePrintClassifier.exactMatchDistance` of a candidate decides it alone (`ElementJudgement.isExactMatch`), so one rejection or correction holds on the next run. Learned detector (step C): the reviewer's workflow window trains on complete reviews and promotes only on held-out gains (`DetectorPromotion`, `ModelRegistry` under `<bank>/models`); the active model proposes through `LearnedCandidateSource`; readiness, estimate and offer state in `models/training-state.json`. Dataset semantics and split handling: `Chevron7/docs/security-element-training.md`.

- **App Shell (RootView.swift)**: Minimalist sidebar with primary sections (Podpisovanie, Zarucena konverzia, Register konverzií), collapsible history sections (signed and recent documents) showing five rows with "Zobraziť všetky", clean-up that can move kept copies to the Trash (`SignedDocumentStore`, retention `webSigningRetentionDays` for browser copies only), a collapsible "Zaručené konverzie" section under the signed documents (hidden while the register is empty) with the five newest register rows by conversion time, each with its name (`originalName`, else `newDocumentName`), evidence number and EZZK state symbol in the Register's wording and tone (`SidebarConversionRows`, `UXLabels.evidenceStatusLabel`, `EZZKRecordPresentation.tone`), redrawn on `EZZKStatusChecker.changeCount` and ZaKo's step because `LocalEvidenceStore` is not observable; a row opens its detail in the Register (`EvidenceDashboardView.requestedRecordID`) and "Zobraziť všetky" opens the Register, bottom card reader status indicator (`SmartcardHUDStatus`, with the card kind from `SigningIdentityInfo.cardKindLabel`) on an opaque bar, fed in every section by one `CardReaderStatus` poll on the app model (only while the app is active and nothing talks to the card; it also feeds `SigningSessionStore.applyReaderIdentities`, and `SmartcardBadge` lets each section's store pick the certificate to name) above the quiet "Pridať súbory…" and "Nastavenia" rows (one icon column, `SidebarMetrics.iconWidth`) and the official yellow Buy Me a Coffee button (`Assets/BuyMeACoffee.png`, copied into Contents/Resources by `build_app.sh`, the same image as the website; `DonateButton` falls back to a drawn yellow button when the bundle lacks it) opening `AppLinks.donate`, the same as the Help menu's "Podporiť vývoj…", with its Slovak tooltip and accessibility label in `SidebarDonateLink` (only the main window has it); the "Zaručené konverzie" rows lead with their EZZK state symbol, Full Keyboard Access focus rings, signing queue management, and step-aware window subtitles.
- **Signing Suite (SigningFlowViews.swift)**:
  - `SigningIntakeView`: Clean dropzone with `DropzoneArtwork`, support chips, and `⌘O` shortcut.
  - `SigningPrepareView`: PDF preview, collapsible/resizable inspector (`MacOS27Layout.inspectorIdealWidth`), and sticky action bar with `Podpisat KEP` (`⌘⏎`) and `VisibleAppearanceInspector`. The toolbar offers document reset and inspector visibility; document reset is disabled while signing. Visible signature cards have a transparent background.
  - `SigningDoneView`: Result summary with `EIDASBadge` and Quick Look / Finder actions.
  - `SigningBatchView`: "Nastavenie dávky" is one native columns form (certificate, PIN, PAdES / ASiC-E, packaging, QTS with the TSA menu, PDF/A, visual stamp read from the document screen), disabled once the batch starts. An ASiC-E batch writes a container per document or one shared container named in the card (`AppSettings.batchASiCPackaging`, remembered, default per document; `BatchSettingsSnapshot.containerStem`). While the batch is ready, `refreshReadyBatchOptions` takes every option change in and replans the outputs without reading the card again; an invalid TSA keeps it ready but unable to start (`batchOptionsError`, `batchCanStart`).
- **ZaKo Advocate Studio (ZakoFlowViews.swift, AnalysisCanvasView.swift, AttestationFormView.swift, AuthorizeDoneViews.swift)**:
  - `AnalysisCanvasView`: Markup tools with keyboard placement (`Pridať na aktuálnu stranu`), accessible element selection rows, and left thumbnail strip adapting to page aspect ratio. ZaKo toolbar reset and backward navigation from authorization are disabled while authorizing.
  - `AttestationFormView`: Deduplicated advocate profile fields, live clause preview, and template menu.
  - `AuthorizeView`: Mandate certificate verification, PIN handling, and sticky authorization action bar.
  - `DoneView`: Finder access to the output folder and "Uložiť ako…" for the delivered file (the client ASiC-E, `EvidenceRecord.deliveredFileName`).
- **Evidence Dashboard (EvidenceDashboardView.swift)**: Native `.searchable` search, segmented status picker, SQLite table with right-click context menu, and confirmation dialog for deletions.
- **Settings (SettingsView.swift)**: `TabView` styled with `.tabViewStyle(.sidebarAdaptable)` for macOS sidebar navigation.
- **Web Signing (WebSigningPrompt.swift, WebSigningSheet.swift)**: Floating resizable `NSPanel` with window close delegation, trusted origin badge, and bounded PDF/XML preview.
- **Signing an already signed document (`SigningSessionStore`, `ExistingSignatureGuard`)**: the source's own bytes decide (`/ByteRange` for a PDF, an `.asice` zip for a container), never the engine's inspection, so the guard also holds in Demo. A signed PDF or a container is handed over unchanged: no PDF/A, no stamp baked in through PDFKit (both dropped the existing PAdES signature); a signed PDF preselects PAdES, where the engine draws the stamp as an incremental update. A container goes to the engine under its own name and is extended (`buildForExistingASiC`), only with a provider whose `addsSignatureToExistingContainer` is true and never by phone; a batch refuses containers. Every main-window request sets `filename` and `signsExtraFilesAsDataObjects`, so the engine builds the ASiC-E around the PDF itself instead of wrapping a packaged `kontajner.asice` (the nesting found on the web path, WEB-SIGNING-FINDINGS section 6).
- **ZaKo only with a mandate certificate (`ZakoMandateCardFlow.swift`, `MandateCertificate`, `ZakoCardPromptSheet`)**: one rule decides an MQC for every scanner (`MandateCertificate.matches`: "OPRÁVNENIE" as I.CA names the SAK mandate certificate, or "mandát"; never a public CA; a QESIG certificate without the token no longer counts). Outside the Demo signing provider, "Získať číslo" outside EZZK Demo and "Autorizovať konverziu" walk a card flow (`beginAuthorization`, `advanceCardFlow`; `requestEvidenceNumber` remains for the gate but no button calls it: `authorizeAndSign` allocates the number itself after the MQC, right before signing, `needsFreshEvidenceNumber`): no card raises "Vložte kartu" and waits for it (`waitForCard`); a number needs only the MQC CryptoTokenKit shows without a PIN (`MandateCertificate.currentCardState`, `ZakoSessionStore.mandateGate`); a signature reads the certificates with the PIN (asked in a sheet) or the eID's BOK and selects the MQC; a card without one is refused. The flow resolves a PIN exactly once (never `refreshIdentities`, which retries a remembered PIN). `fetchEvidenceNumber` and `authorizeAndSign` refuse on their own too, and the non-mandate override is left only to the Demo provider. The PIN lives for the app run in memory (a new document keeps it) and is dropped when the reader reports no card or the card refuses it. The shared `CardReaderStatus` poll feeds ZaKo (`applyReaderIdentities`) so the clause step shows the card.
- **Signing engine (`engine/`, `Chevron7/scripts/build-engine.sh`)**: EUPL fork of slovensko-digital/autogram (DSS, PKCS#11, machine protocol v1/v2) plus the C launcher and Swift Quick Action runner; built into a jlink arm64 runtime and bundled by `build_app.sh`. Machine mode SIGKILLs itself after the terminal event, so exit 137 after `session.completed` is expected.
- **Finder Quick Action (`Assets/Chevron7 Finder Quick Action.workflow`, `build_app.sh`)**: Automator workflow restricted to Finder via `NSRequiredContext`; runs `chevron7-quick-action.sh` and the bundled legacy CLI helper in the background, with `AutogramCLI-arm64`, `AutogramQuickActionRunner-arm64`, JAR dependencies, and Java runtime bundled in the app. The flow shows driver, certificate, and PIN/BOK dialogs without opening the main app and accepts PDF files only. Every launch reinstalls it (`FinderQuickActionService.installQuickAction`) and first moves the old Autogram macOS Quick Action (`Autogram Finder Quick Action.workflow`, recognised by its `autogram-cli-sign.sh`) to the Trash when no Autogram macOS app is left to run it, since it would otherwise fail with "Autogram macOS ARM64 helper was not found". The runner's messages carry no product name, because the rename boundary keeps Chevron7 out of `engine/`. Finder shows it under Quick Actions only when its `pbs` `NSServicesStatus` entry has `presentation_modes` (`FinderQuickActionService.servicesStatus`); the pre-Mojave `enabled_*` keys are ignored.

## Build & Test Instructions
- Build the signing engine first (once, or after changes in `engine/`): `scripts/build-engine.sh` (needs an arm64 JDK 25 with JavaFX jmods, Azul Zulu FX 25, under `~/Library/Java` or `AUTOGRAM_JAVA_HOME`; output `.build/engine/Contents`)
- Run build script: `DEVELOPER_DIR="/Applications/Xcode.app/Contents/Developer" ./build_app.sh [--release] [install]` (bundles `.build/engine/Contents` into `Contents/{Helpers,app,runtime}`; without it signing falls back to Keychain/DEMO and the Quick Action cannot sign)
- Run test suite: `DEVELOPER_DIR="/Applications/Xcode.app/Contents/Developer" swift test`
- Tests never touch the real `~/Library/Application Support/Chevron7` (the evidence register is a legal record) or `~/Library/Caches/Chevron7`: App tests build settings with `makeSettingsStore()` (a temporary `AppSettingsStore.storageRoot`, from which evidence, vision bank, output, templates and signature images derive), Kit tests pass `directory:` / `cacheRoot:` / `applicationSupportRoot:`. `RealStorageGuard` (`Tests/Chevron7TestSupport`, installed when the test bundle loads) fails any test that changes either folder, and `RealStorageGuardTests` rejects test sources that build a store on the default root. Tests never write a named `UserDefaults` suite either (it stays in `~/Library/Preferences` for good): pass `MemoryUserDefaults()` (`Tests/Chevron7TestSupport`) to any `defaults:` parameter; the guard also fails a test that creates or changes a `~/Library/Preferences` plist named after a test class (such as `SigningBatchTests.<UUID>.plist`), and the source scan rejects `UserDefaults(suiteName:` in tests. Nor do tests use `UserDefaults.standard`, which under XCTest is the runner's own domain (`~/Library/Preferences/com.apple.dt.xctest.tool.plist`, shared by every run): `AppSettingsStore` and `AppSettings.load(defaults:)` / `save(to:)` take the defaults, `makeSettingsStore()` passes a `MemoryUserDefaults()`, and the guard fails a test that changes a key of that domain
- Probe the AVM server end to end: `swift run avm-probe <file.pdf|file.asice> [--level PAdES_BASELINE_T] [--container ASiC-E] [--out <dir>] [--timeout <s>]` (prints the QR link, opens the QR PNG, waits for the phone, prints signers)
- Probe EZZK: `swift run ezzk-probe <login|time|numbers|consume|lookup|record|receive> [number] [--env test|production] [--name N] [--ico I] [--at ISO] [--purpose original|xml] [--out FILE] [--file ASICE]` (credentials from `EZZK_LOGIN`/`EZZK_PASSWORD` or the Keychain item Settings saved; `numbers`, `consume` and `receive` refuse production; `record` reads one of the person's own records with `GetConversionRecord` and changes nothing)
- Run detection eval harness: `swift run vision-eval <dataset> [--builtin-only] [--no-fm] [--bank <dir>] [--iou 0.4] [--json] [--model <Detector.mlmodel>]` (dataset export kept outside the repo; `--bank <dir>` picks the example bank, default is a fresh empty temporary directory; `--model` adds the learned source)
- Releases: `.github/workflows/release.yml` publishes a GitHub release on every push to main with a feat, fix or perf commit since the last `native-v*` tag (runner `xcode-27`, Zulu FX 25 via setup-java). `Chevron7/scripts/next-version.sh` derives the version, `build_app.sh --release package` keeps the Safari extension for the DMG (`CHEVRON7_VERSION`, else the last tag), `scripts/package-release.sh VERSION` builds `Chevron7-vX.Y.Z.dmg` with `Install Safari Bridge.command` and `SHA256SUMS.txt`, and `scripts/release-notes.sh` prefers a hand-written `docs/releases/vX.Y.Z.md`. `[skip release]` in a commit message keeps it out. Nothing is committed back.
- Binary output: `$(swift build --show-bin-path)/Chevron7.app` (Xcode 27: `.build/out/Products/Debug/Chevron7.app`)
